# Editor Requirements

**Status:** Draft requirements for the OpenUX editor; not normative.

The browser editor prototype is at the repository root; its sample project is in `openux/`. The prototype is exploratory and is used to try ideas and evaluate the intended experience. Its implementation choices and limitations are not requirements for the final product. This document describes the target product and should evolve as those requirements are refined.

| ID | Target requirement |
|---|---|
| ED-001 | Open an OpenUX project and resolve its Screens, discovered Assets, Theme, optional project-level and Element-linked Markdown behavior specs, and supporting resources. Discover shared Assets under `assets/` and Screen-owned Assets under `screens/<screen-id>/assets/`; do not require an Asset registry in `project.yml` or the prototype's `/openux/` HTTP serving arrangement. |
| ED-002 | Validate project structure and references on load, and make missing or invalid artifacts clear to the user. |
| ED-003 | Provide a selectable Project Overview with summaries of its Screens, Assets, Theme, and attached behavior specs. Show a collapsible file tree mirroring the project structure. Open supported files in their corresponding Studio views and keep selection consistent. Let users add text directly and drag image or template Assets from the file tree to the Screen or a template's named slot. |
| ED-004 | Keep the details inspector focused on the current selection: Project, project-level behavior spec, Theme, Screen, template Asset, or selected Element. Do not mix unrelated entity details. |
| ED-005 | Render Screen previews using text and image Elements, template Assets, local resources, and project Theme CSS and tokens. Size the preview to the available browser viewport rather than constraining it to a device mockup. Contain fixed-position overlays so project UI cannot cover or visually alter Studio chrome. Support template slots containing nested Elements. |
| ED-006 | Provide schema-driven editing for template attributes: text for `string`, checkbox for `boolean`, single-choice dropdown for `list`, and numeric input for `number`. Support `integer`, `decimal`, `currency`, and `percentage` number formats. |
| ED-007 | Resolve `${attributes.<name>}` placeholders from an allowed Element override or the template default. Insert values safely as text or attribute values, and report undeclared references. |
| ED-008 | Edit Screen metadata, Elements, template Asset definitions, and Theme values. Only permit overrides that the template declares as overridable. |
| ED-009 | Apply project Theme styles only to rendered project previews through shared semantic class names and tokens. Scope Theme CSS to preview content so project Themes cannot alter the editor interface. |
| ED-010 | Let users open the single Markdown behavior spec attached to an Element by double-clicking it in the Screen preview. Store Element specs directly in `screens/<screen-id>/specs/` as `element-<element-id>.md`, with `element-id` front matter. Opening an Element without a spec starts an unsaved draft; save it only when changed, and discard an unchanged draft when the user leaves. Attach specs to Screen Elements, not Screen mappings or Asset definitions. Require OpenSpec's structured Purpose, Requirements, and scenario format; treat specs as declarative behavior contracts, not executable actions or implementation plans. |
| ED-011 | Let a human inspect rendered results and record a review outcome for the relevant Screen, Element, or Theme. |
| ED-012 | Provide an explicit save action. The editor frontend sends changes to a Node.js server, which validates and writes them back to project files; the frontend does not write to the filesystem directly. Confine writes to the opened project root and report save failures. |
| ED-013 | Preserve project information when reading and writing files, including unknown fields or content the editor does not support. Never silently discard data or break compatibility. |
| ED-014 | Provide reliable error feedback for invalid values, unsupported features, missing files, and failed saves; do not silently substitute success-shaped results. |
| ED-015 | Support undo/recovery for user edits and allow the user to reload or revert to saved project data. |
| ED-016 | Let users move Elements between Screen roots and template slots, reorder sibling Elements by drag and drop, and delete a selected Element. Provide a context menu on template Elements to edit the template Asset, copy prompt-ready Element details, or delete the Element after confirmation. Do not require a root layout. |
| ED-017 | Create a Screen with a unique project ID and file, add it to the project manifest, and leave it empty so the user can add text or drag an image or template Asset onto the canvas. |
| ED-018 | Expose machine-readable context on each Element and standalone template Asset preview so browser inspection and automation can identify its owning Screen, Element ID and type, referenced Asset path, and Element name. Slot-bearing templates must not put child Elements behind a Shadow DOM boundary; scope template, Theme, and editor styles to each template Element. |
| ED-019 | Expose the current Screen ID and name on each Screen manifest file-tree entry and on major Screen-view containers, including the workspace context, main canvas, stage, and preview. Use the `data-openux-screen-id` and `data-openux-screen-name` attributes defined in `screen.md`; omit Screen context when previewing a standalone template Asset. |
| ED-020 | Adapt the Studio interface to the operating system's light or dark color scheme, independently of the active project Theme, and respond to system preference changes while open. |
| ED-021 | Support one optional project-level OpenSpec-formatted behavior spec referenced by `project.spec` for requirements that apply across multiple Screens or throughout the project. Let users create or edit it from the Project Overview and persist a new file and manifest reference together only when its draft changes; discard an unchanged new draft when the user leaves it. Do not use it for Screen-specific behavior. |
| ED-022 | Let each Screen define named visual preview states, require a description for every non-default state, and switch the preview between them without altering authored defaults. Require each non-default state to be referenced with `SHOW <state-id>` after `THEN` in a Screen-level or linked Element spec. Selecting a state shows its name, description, actions, and per-Element visibility controls. Allow selecting hidden Elements from the Screen element tree. |
| ED-023 | Provide a searchable Screen selector at the top of the file explorer, with available Screens searchable by name or ID. Selecting a Screen opens it, expands its path, and selects its `screen.yml` file. |
| ED-024 | Represent the active editor file in the URL and add a browser history entry when navigation changes to a different file. Back and Forward must restore the corresponding editor and selection without adding entries for edits within the same file. |
| ED-025 | Define each template Asset in one `<template-id>.stml` file directly inside an `assets/` directory, with a required YAML front matter mapping and HTML body. Discover image and supporting resource files from the same directory tree. Validate template headers without requiring a separate Asset registry or `asset.yml` file. |

## Target Page Layout (Proposed)

Use the current prototype's page structure as a starting point: a global header above a three-part workspace. This describes the intended information hierarchy, not fixed dimensions or a requirement to copy the prototype's visual styling.

- **Global header:** Show the product and current Screen or template context, plus project-wide actions and status such as save, undo, and unsaved changes.
- **Project files:** Provide a persistent, collapsible file explorer that mirrors the OpenUX project hierarchy. Show discovered Assets under their shared or Screen-owned `assets/` directory. Let users drag image and template files into the Screen or a named template slot.
- **Main canvas:** Give the selected Screen or template preview the primary workspace. Keep review results and interaction feedback close to the preview without obscuring it.
- **Details inspector:** Place selection-specific details and editing controls beside the canvas. Show only the currently selected Theme, Screen, template Asset, or Element; when nothing is selected, show a clear prompt.
- **Responsive behavior:** Preserve access to navigation and details on narrow screens by moving them into accessible collapsible panels or tabs. Do not simply remove these areas; prioritize the canvas and allow it to scroll or resize as needed.

## Prototype Context

The current prototype uses a local Node.js server to serve the editor and persist changes to the `openux/` example project. Its sidebar lists project files in a collapsible tree. A searchable Screen selector switches Screens. Selecting `project.yml` opens the Project Overview; a Screen manifest opens its Screen with Preview and editable YAML views; Theme files open the Theme view; `.stml` template Asset files open the template editor; and linked Markdown specs open the spec editor. Screen YAML edits are parsed before they update the preview, and valid source is persisted on explicit save. Image and template Assets can be dragged from the file tree; text can be added directly. Template Assets are single `.stml` documents with YAML front matter and an HTML body, stored directly in shared or Screen-owned `assets/` directories. Assets are discovered from those directories rather than listed in `project.yml`. A Screen-owned template dragged to another Screen is copied into that Screen's `assets/` directory on save. Element specs live directly in `screens/<screen-id>/specs/` as `element-<element-id>.md` and link with `element-id` front matter. The server only allows edits to supported files under the example project. These are prototype constraints, not target-product requirements. The product's supported file formats, review-state persistence, and currency/locale behavior remain open design decisions.

When a behavior spec is open, selecting another Element in the preview keeps the Spec editor and preview visible and opens that Element's spec, or starts a draft if it has none. If the user switches away from an unchanged draft, discard it and remove it from the file tree.

File selections are reflected in the URL and browser history. Back and Forward restore the corresponding editor; changing the Screen preview/YAML subview or selecting an Element within the same Screen does not create another file-navigation entry.
